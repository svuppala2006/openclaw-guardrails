What is the MOC?

The Mass Open Cloud (MOC) Alliance is a collaboration between universities, government, and industry to build and operate a production public cloud for research.

New England Research Cloud (NERC)

The MOC's flagship platform — a shared OpenShift-based cloud hosted at the Massachusetts Green High Performance Computing Center (MGHPCC). It serves researchers across Boston University, Harvard, MIT, Northeastern, and UMass.

Open & Multi-Tenant

Unlike private clouds, the NERC is a shared environment. Multiple research teams run workloads side by side, which makes security and isolation critical for any new deployment.

Deploying AI agents here means they must be secure enough to coexist with other researchers' workloads.

The Problem

OpenClaw is an AI agent gateway that gives LLMs the ability to execute code, call APIs, and interact with infrastructure. Deploying it on shared research clusters raises serious security questions.

Secret Leakage

Snyk found 7% of OpenClaw skills have critical credential vulnerabilities. API keys sit in plain-text environment variables.

Prompt Injection

A malicious prompt could instruct the agent to delete files, exfiltrate data, or execute arbitrary code on the cluster.

Unrestricted Access

Without sandboxing, agent-generated code has full access to the gateway process, credentials, and the Kubernetes API.

Is it even worth deploying OpenClaw on the MOC?

My Approach: Defense in Depth

No single tool solves everything. I implemented multiple independent security layers — if one fails, the others still protect the system.

Input/Output Guardrails

NeMo Guardrails (Sidecar)

NVIDIA's guardrails engine runs as a sidecar proxy inside the OpenClaw pod. Screens every request and response using Colang rules.

Detects: Jailbreaks, prompt injection, abusive language, off-topic requests

TrustyAI Orchestrator

Red Hat's content safety platform with built-in detector models for PII and harmful content classification.

Detects: PII (emails, SSN, phone, credit cards), hate speech, toxic content

Performance Impact: ~70–120ms added latency per request · +100–250m CPU · +256–512Mi memory

Network Isolation & Egress Control

Ingress Policies

Default-deny ingress with 3 allow rules: only the OpenShift router, guardrails orchestrator, and NeMo can reach OpenClaw.

AdminNetworkPolicy

Pod-level egress restrictions. OpenClaw can only reach DNS (53), Kubernetes API (6443), and HTTPS (443). Everything else is blocked.

EgressFirewall

DNS-based allowlist for external destinations. Only approved domains (Vertex AI, container registries) are reachable.

Contributed a wildcard DNS fix to nerc-ocp-config (PR #963) to work around OVN-Kubernetes limitations.

Agent Sandboxing

NVIDIA OpenShell

Per-session sandboxing: each agent session gets its own disposable Kubernetes pod. Agent-generated code runs in complete isolation from the gateway.

Deployed on AWS cluster

NemoClaw

Self-sandboxed alternative: the entire OpenClaw process runs in a restricted pod with all capabilities dropped, non-root, seccomp, and SELinux isolation.

Simpler architecture, suitable for single-user

Challenges & Lessons Learned

No Cluster-Admin Access

Could not install operators, create ClusterRoleBindings, or grant SCCs. Had to find creative alternatives and work with cluster admins for every cluster-scoped change.

Network Policy Blockers

AdminNetworkPolicy blocked pod-to-pod communication. Required iterating with cluster admins to open specific ports while maintaining security.

OVN-Kubernetes Limitations

Wildcard DNS rules aren't supported in EgressFirewall. Contributed a fix upstream (nerc-ocp-config PR #963) to work around this.

First OpenClaw on MOC

No prior deployments to reference. Built everything from scratch, documented all experiments (including failures) in the openclaw-guardrails repo.
